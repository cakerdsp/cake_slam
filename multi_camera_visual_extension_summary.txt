Cake-SLAM 多相机视觉扩展核心讨论总结
========================================

整理日期：2026-06-18


一、目标与已确定的前提
----------------------

1. 将当前单相机视觉模块扩展为同步多相机视觉模块。

2. 所有相机具有相同时间戳，并且假设这些时间戳对应同一个实际曝光时刻。
   需要注意：消息时间戳相同并不天然等价于实际曝光同步。如果相机是硬件触发同步，
   或已经验证驱动时间戳语义，则可以认为多个相机共享同一时刻的机体状态。

3. 每个相机顺序执行以下工作：
   - 当前图像预处理；
   - 可见地图点检索；
   - 参考patch选择；
   - 当前patch或虚拟patch构造；
   - 光度残差和雅可比构造。

4. 任意单个相机完成残差构造后，不立即修改状态。
   所有相机必须基于同一个状态线性化点构造残差，然后进行一次联合状态更新。

5. 多个相机使用统一的视觉地图：
   - 世界坐标系中的VisualPoint是共享的；
   - 同一个VisualPoint可以包含来自不同相机、不同时间的多个观测；
   - 参考patch允许跨相机选择，不要求参考patch和当前图像来自同一相机。

6. 每个相机拥有独立且固定的：
   - 相机模型和内参；
   - 相机到IMU的外参；
   - 图像尺寸；
   - 像素到单位射线LUT；
   - 图像网格、深度图和虚拟patch临时缓存。


二、当前项目中的单相机假设
--------------------------

当前代码中的以下部分都是单相机设计：

1. LIVMapper只维护一组图像订阅、图像缓存和图像时间戳缓存。

2. MeasureGroup中只保存一张cv::Mat图像。

3. LIVMapper只创建一个VIOManager。

4. VIOManager内部同时保存：
   - 一个相机模型cam；
   - 一组相机外参Rci/Pci；
   - 一个当前帧new_frame_；
   - 一套图像网格和射线LUT；
   - 一个视觉地图feat_map；
   - 一个当前视觉子图visual_submap；
   - 残差、雅可比和EKF更新缓存。

5. 当前processFrame()将以下阶段耦合在一个函数中：
   - 查询视觉地图；
   - 构造参考patch和当前patch；
   - 构造残差和雅可比；
   - 立即执行EKF状态更新；
   - 生成新视觉点；
   - 更新已有视觉点观测；
   - 更新参考patch。

因此，多相机扩展的关键不是简单地循环调用多个processFrame()。
如果逐相机调用现有processFrame()，前一个相机会提前修改状态和地图，后一个相机看到的
线性化状态与地图就已经不同，这不符合计划中的联合优化模型。


三、推荐的总体模块划分
----------------------

建议将视觉部分拆分为以下职责：

1. RigSynchronizer
   - 维护每个相机的订阅和图像队列；
   - 按统一时间戳组装MultiCameraFrame；
   - 处理相机缺帧、超时和丢帧策略。

2. CameraContext
   每个相机一个实例，保存：
   - camera_id；
   - 相机模型；
   - T_camera_imu外参；
   - 当前图像和图像金字塔；
   - 图像尺寸、网格和遮挡深度图；
   - 像素到单位射线LUT；
   - 虚拟patch参数和工作区；
   - 当前相机临时观测集合；
   - 每相机统计和健康状态。

3. SharedVisualMap
   - 唯一拥有所有VisualPoint；
   - 管理体素索引；
   - 管理每个地图点的多相机观测；
   - 提供只读查询和批量提交接口；
   - 负责新点去重、观测裁剪和生命周期管理。

4. MultiCameraVIOCoordinator
   - 持有共享IMU/机体状态；
   - 组织每个相机顺序构造观测；
   - 保证构造残差期间地图只读、状态不变；
   - 调用联合优化器；
   - 状态更新完成后统一提交地图修改。

5. JointVisualOptimizer
   - 接收各相机的临时观测；
   - 在每个金字塔层和每次IESKF迭代中重新线性化全部有效相机；
   - 累加联合正规方程；
   - 统一求解状态增量和更新协方差。


四、推荐的完整数据流
--------------------

阶段A：同步与状态预测

1. 按时间戳组装一个MultiCameraFrame。

2. IMU只传播一次，传播到该组相机图像的统一曝光时刻。

3. 由同一个预测机体位姿，根据每个相机的固定外参计算：

   T_camera_i_world = T_camera_i_imu * T_imu_world

主程序组装同步相机包时需要注意：

1. 每个相机必须维护独立的图像队列和last_timestamp，不能继续共用当前单相机的
   last_timestamp_img。

2. 当前代码存在“相邻图像时间小于0.02秒则丢弃”的检查。如果多个相机共用这一检查，
   第二个到达且时间戳相同的相机图像会被错误丢弃。该检查必须改成每相机独立执行。

3. 不建议使用double时间做严格相等比较。应使用ROS时间戳的整数纳秒值作为rig frame键。

4. 相机消息的到达顺序可以不同。只有同一个时间戳下所有必需camera_id的图像都到齐后，
   才生成一个MultiCameraFrame。

5. sync_packages()仍然只需要使用该MultiCameraFrame的一个统一时间戳切分一次LiDAR和IMU，
   不需要为每个相机重复传播或重复切分传感器数据。

6. MeasureGroup应保存一个MultiCameraFrame或图像数组，而不是单张cv::Mat。

7. VIO阶段结束时，应原子地移除该时间戳对应的整组图像，不能只弹出其中一个相机队列。

8. 即使假设数据严格同步，也应设置缺帧超时和队列上限，防止某个相机异常后主循环永久等待。


阶段B：地图快照和逐相机观测准备

1. 将共享视觉地图置为只读状态。

2. 对每个相机顺序执行：
   - 创建当前CameraFrame；
   - 构造该相机的深度图或范围图；
   - 查询该相机视场内的共享VisualPoint；
   - 做遮挡、边界、视角和纹理检查；
   - 从地图点的参考候选中选择最合适的参考patch；
   - 构造当前虚拟patch支持区域；
   - 保存临时观测，但不修改地图和状态。


阶段C：多相机联合优化

对于每个金字塔层和每次IESKF迭代：

1. 固定当前迭代的统一状态线性化点。

2. 清空联合正规方程A和b。

3. 顺序处理每个相机的有效观测，累加：

   A += H_camera^T * W_camera * H_camera
   b += H_camera^T * W_camera * residual_camera

4. 所有相机完成后，只求解一次联合状态增量。

5. 更新共享状态。

6. 如果未收敛，则所有相机都基于最新共享状态重新线性化。

注意：
不能在所有相机只构造一次残差后，整个视觉帧只做一次非迭代更新。
直接光度残差具有明显非线性，当前代码也使用金字塔和多次迭代，因此多相机版本应保持
“每一层、每一轮迭代中进行一次多相机联合更新”。


阶段D：统一提交地图修改

联合优化结束后：

1. 使用最终状态更新所有相机的当前位姿。

2. 汇总所有相机对已有地图点产生的新观测。

3. 合并所有相机生成的新点候选，先去重，再创建VisualPoint。

4. 为同一个VisualPoint挂接来自多个相机的观测。

5. 更新参考patch候选、点法向、收敛状态和观测质量。

6. 执行地图点和观测的裁剪。

地图修改必须在联合状态更新完成后统一执行，否则相机处理顺序会影响最终结果。


五、联合优化的数学形式
----------------------

对于第i个相机的第j个有效光度残差：

   r_ij(x) = I_current_i(project_i(x)) - I_reference(warp_reference)

其中所有相机共享同一个机体状态x，但每个相机使用自己的相机模型和外参：

   T_camera_i_world(x) = T_camera_i_imu * T_imu_world(x)

联合目标函数为：

   min_x sum_i sum_j rho(r_ij(x)^T * W_ij * r_ij(x))

多个相机的残差可以直接堆叠，也可以累加正规方程。推荐累加正规方程，因为两者在相同
独立噪声假设下等价，但累加方式不需要分配巨大的H矩阵。

当前视觉测量主要直接约束：

1. 共享机体旋转，3维；
2. 共享机体位置，3维；
3. 当前相机的光度尺度，在开启曝光估计时加入。

速度、IMU偏置和重力没有直接光度雅可比，但可以通过EKF交叉协方差被间接修正。


六、跨相机patch在数学上是否成立
--------------------------------

跨相机patch在数学上成立，本质上属于多相机直接法或多相机光度优化。
参考patch和当前图像不需要来自同一个物理相机。

对于参考patch像素u_ref：

1. 使用参考观测的投影模型和局部平面/深度，将u_ref恢复为对应的三维表面点；

2. 将该三维点变换到当前相机；

3. 使用当前相机模型投影到当前图像；

4. 比较参考亮度和当前亮度。

成立需要以下条件：

1. 两个相机的内参和畸变模型准确；
2. 相机到IMU的外参准确；
3. 相机时间同步；
4. 地图点深度或局部平面法向可用；
5. 局部表面近似平面，或者使用了足够准确的三维几何；
6. 光度响应已经标定或通过光度参数补偿；
7. 当前观测不存在严重遮挡、镜面反射或运动物体干扰。


七、跨相机虚拟patch的关键坐标问题
----------------------------------

需要区分两种“共光心”：

1. 同一个物理相机内部：
   原始相机和由它构造的虚拟相机共用该物理相机光心，因此两者之间只有旋转。

2. 不同物理相机之间：
   两个虚拟相机分别位于各自物理相机的光心，因此它们之间通常同时存在旋转和平移。

所以跨相机patch不能只使用旋转R_virtual_current_virtual_reference，而必须使用完整SE(3)：

   T_virtual_current_virtual_reference
       = T_virtual_current_world * inverse(T_virtual_reference_world)

其中的平移部分来源于多个物理相机之间的基线。
如果忽略该平移，在存在视差时数学模型不成立。

更具体地，约定T_A_B表示“将B坐标系中的点变换到A坐标系”，则跨相机虚拟坐标系的
完整变换链为：

   T_Vcurrent_Vreference
       = T_Vcurrent_Ccurrent
         * T_Ccurrent_Creference
         * T_Creference_Vreference

其中物理相机之间的变换为：

   T_Ccurrent_Creference
       = T_Ccurrent_IMU * inverse(T_Creference_IMU)

T_Vcurrent_Ccurrent和T_Creference_Vreference只负责物理相机坐标系与其局部虚拟坐标系之间
的旋转，平移为零。真正的相机基线平移位于T_Ccurrent_Creference中。

虽然多个相机时间戳相同、机体没有帧间运动，但两个物理相机的光心在机体上具有固定空间
间隔，所以该平移不会因为时间同步而消失。对于参考虚拟坐标系中的三维点p_Vreference：

   p_Vcurrent = R_Vcurrent_Vreference * p_Vreference
                + t_Vcurrent_Vreference

如果两个相机光心不重合，t_Vcurrent_Vreference通常不为零。

完整变换还必须与地图点深度或局部平面结合，才能正确处理跨相机视差。


八、“参考patch相机无关”的准确含义
--------------------------------

讨论中所说的“参考patch相机无关”，建议准确表述为：

   参考patch存储在共享视觉地图中，参考观测的选择不受相机身份限制；
   但是每个参考观测仍然保留生成它的源相机信息、位姿和patch坐标系。

原因是当前虚拟patch的局部坐标轴由“参考相机光心指向地图点”的方向构造。
因此patch可以被任意当前相机使用，但参考虚拟坐标系仍然与生成它的参考视角有关。

推荐地图点保存少量覆盖不同观察方向的参考候选，而不是永久只保存一个全局参考patch。
当前相机可以从全部候选中选择：

1. 观察方向最接近的候选；
2. 仿射变形较小的候选；
3. 纹理和NCC质量较高的候选；
4. 遮挡风险较低的候选；
5. 不限制候选来自哪个物理相机。

如果希望patch坐标系在严格意义上也与相机无关，则需要把patch定义在地图点的世界系局部
切平面上，建立稳定的世界系切向基。这种“地图规范patch”更标准，但需要额外处理：

1. 切向基的稳定定义；
2. 不同视角图像向规范平面的重采样；
3. 多次观测的纹理融合；
4. 遮挡和非朗伯特表面；
5. 地图法向更新后patch坐标系是否跟随更新。

第一版可以继续使用参考观测对应的虚拟patch，只要保存完整T_virtual_world信息即可。


九、共享视觉地图的数据结构变化
--------------------------------

世界点层可以继续保存：

1. 世界坐标位置；
2. 法向；
3. 点协方差；
4. 法向信息；
5. 收敛状态。

主要变化发生在观测层。

建议的VisualPoint概念结构：

   VisualPoint
   {
       position_world;
       normal_world;
       covariance;

       observations;
       reference_candidates;

       last_seen_rig_frame_by_camera;
       unique_rig_pose_count;
       visibility_camera_mask;
       convergence_statistics;
   }

建议的PatchObservation概念结构：

   PatchObservation
   {
       camera_id;
       rig_frame_id;
       timestamp;

       T_camera_world;
       T_virtual_world;

       pixel;
       bearing;
       view_direction_world;

       core_patch;
       virtual_support;
       patch_size_and_scale;

       inverse_exposure;
       quality_score;
       residual_statistics;
   }


十、当前地图结构在多相机下会出现的问题
--------------------------------------

1. 当前Feature没有camera_id。
   多相机版本必须增加camera_id或等价的稳定相机标识。

2. 当前Feature::id_通常是当前相机帧ID。
   不同相机可能在同一个rig frame使用相同帧ID，因此唯一标识应采用：

   (rig_frame_id, camera_id)

3. 当前VisualPoint只有一个ref_patch和一个has_ref_patch_。
   多相机版本至少需要一个参考候选集合，而不是简单的单一全局裸指针。

4. 当前参考patch选择会在全部观测之间计算NCC。
   跨相机允许这样做的前提是完成光度标定或亮度归一化；否则不同相机的响应差异会影响评分。

5. 当前部分逻辑通过obs_.size()判断地图点是否收敛。
   多相机同一时刻可能给同一个地图点添加多条观测，但这些观测只对应一个机体位姿。
   因此收敛判断应该统计：
   - 不同rig frame数量；
   - 不同机体位姿数量；
   - 有效基线；
   - 观察方向覆盖；
   而不能仅统计原始观测条数。

6. 当前像素距离更新条件只适用于同一个相机。
   不同相机的像素坐标系不可直接比较，必须和同一camera_id的历史观测比较。

7. 同一个LiDAR候选点可能同时投影到多个相机。
   如果每个相机独立插入地图，会创建重复VisualPoint。
   应先合并各相机的新点候选，再创建一个共享VisualPoint并挂接多个观测。

8. 当前地图和Feature大量使用裸指针。
   多相机共享地图后，建议由SharedVisualMap统一拥有VisualPoint和观测对象，CameraContext仅保存
   非拥有型稳定句柄，避免删除、裁剪和并行读取时出现悬空指针。


十一、曝光/光度参数
------------------

1. 当前项目在线估计一个全局inv_expo_time。

2. 该变量更准确地表示乘性亮度或逆曝光尺度，不一定等价于物理快门曝光时长。

3. 当前参数vio.exposure_estimate_en控制是否在视觉雅可比中加入曝光列。

4. 当前代码默认值为true，仓库中的主要YAML配置也都设置为true。

5. inv_expo_cov控制该变量传播过程中的过程噪声。

6. exposure_time_init是用于图像时间同步的固定时间偏移，不是在线优化的光度变量。


十二、多相机曝光参数的推荐模型
--------------------------------

如果每个相机具有独立曝光或增益，应为当前联合帧中的每个相机维护独立光度参数a_i。

跨相机残差可以写成：

   residual = a_current * I_current - a_reference * I_reference

其中：

1. a_reference保存在历史参考观测中，在当前滤波更新中作为固定值使用；

2. 当前残差由camera_i产生时，只对：
   - 共享机体位姿；
   - 当前相机对应的a_i；
   求雅可比；

3. 该残差不应该更新其他当前相机的曝光参数。

多相机雅可比具有稀疏结构：

   [J_pose, 0, ..., J_exposure_i, ..., 0]

曝光参数不是一定要优化。以下情况可以关闭：

1. 相机使用锁定的手动曝光和增益；
2. 能从驱动读取准确曝光和增益并直接补偿；
3. 相机已完成响应和暗角标定；
4. 使用零均值/单位方差patch或其他曝光不敏感的残差。

如果使用独立自动曝光，建议进行每相机光度估计。

当多个曝光变量同时自由变化时，需要处理尺度规范自由度。可以采用：

1. 固定一个主相机的光度参数；
2. 使用曝光元数据作为先验；
3. 给每个光度参数添加随机游走先验；
4. 将每帧光度参数作为临时变量，通过Schur补消元，而不加入长期IMU状态。


十三、计算量分析
----------------

多相机计算量主要近似随相机数量线性增长：

   O(相机数 * 有效点数 * patch像素数 * 金字塔层数 * 迭代次数)

主要开销通常来自：

1. 地图点投影和可见性判断；
2. 虚拟patch支持区域构造；
3. 参考patch warp；
4. 当前patch采样和图像梯度；
5. 光度残差和雅可比计算。

状态维度仍然很小，因此最终19维左右状态矩阵的求解不是主要瓶颈。
即使加入N个相机曝光参数，求解维度仍远小于像素残差数量。


十四、计算量优化建议
--------------------

1. 流式累加正规方程
   不保存全部相机的巨大H和residual矩阵，逐相机、逐patch累加H^TWH和H^TWr。

2. 设置整套相机的总观测预算
   不要简单地让每个相机都使用当前单相机数量的地图点，否则总残差会按相机数直接膨胀。

3. 平衡相机观测数量
   防止高分辨率或纹理较多的相机完全主导联合优化。

4. 限制同一地图点的同时观测数量
   多个重叠相机看到同一点时，可以按以下指标选择最优的若干相机：
   - 观察角度；
   - 纹理分数；
   - 预测仿射变形；
   - 遮挡风险；
   - 历史残差；
   - 相机覆盖多样性。

5. 每相机独立做视场裁剪
   利用体素索引、相机视锥和深度图尽早排除不可见点。

6. 复用静态数据
   - 像素到单位射线LUT；
   - 虚拟相机支持射线LUT；
   - patch偏移；
   - 固定外参组合；
   都应在初始化时预计算。

7. 控制参考观测数量
   每个地图点只保留少量覆盖不同视角的高质量参考候选。
   虚拟patch模式下每条Feature可能保存局部支持图，观测数量过多会显著增加内存。

8. 先顺序、后并行
   第一版保持每相机顺序线性化，确保结果与相机处理顺序无关。
   接口稳定后，再并行只读的相机残差构造，并在线程局部累加A和b后归并。

9. 使用鲁棒核和每相机健康门限
   单个相机发生模糊、遮挡或曝光异常时，可以跳过该相机，而不是污染整个联合更新。


十五、共享地图的内存管理建议
----------------------------

1. VisualPoint的位置、法向和协方差只保存一份，因此共享地图可以避免重复世界点。

2. patch观测仍然是每相机、每参考视角独立保存的，所以观测内存会随相机数量增加。

3. 建议设置：
   - 每个地图点的最大总观测数；
   - 每个相机的最大观测数；
   - 最大参考候选数；
   - 观测最大存活时间；
   - 质量淘汰规则。

4. 对虚拟patch支持图，可以考虑：
   - 只为参考候选保留完整支持图；
   - 普通历史观测只保留核心patch和统计信息；
   - 统一patch尺寸，避免每条观测存储重复的尺寸元数据；
   - 在验证精度后考虑使用更紧凑的数值格式。


十六、仍需特别注意的问题
------------------------

1. 实际曝光同步
   必须确认相同时间戳对应相同曝光时刻，而不是驱动统一填写的发布时间。

2. Rolling Shutter
   即使帧时间戳相同，不同图像行仍可能对应不同时间。高速运动时需要读出时间模型。

3. 外参误差
   多相机联合残差会把外参误差表现成互相冲突的位姿约束。第一版建议固定高质量离线外参，
   不要同时引入在线外参估计。

4. 光度一致性
   配套相机仍可能存在响应曲线、暗角、白平衡和增益差异。

5. 非朗伯特表面
   镜面、高光和透明区域会导致跨相机亮度不一致，应使用鲁棒核和NCC筛选。

6. 观测相关性
   同一个地图点被多个相机同时观测时，这些残差共享地图点和参考patch，不完全独立。
   如果全部按独立同方差处理，协方差可能过度乐观。可通过限制每点观测数、调整权重或显式
   引入地图点不确定性缓解。

7. 相机失效隔离
   应记录每个相机的有效点数、平均残差、拒绝率和图像清晰度，异常时跳过该相机。

8. 相机处理顺序
   在同一个输入和状态下，改变相机处理顺序后，联合A、b和最终状态应基本不变。
   这应作为重要正确性测试。


十七、建议的实施阶段
--------------------

阶段1：建立单相机回归基线

1. 固定当前数据集和输出轨迹；
2. 记录当前单相机状态、有效点数和残差；
3. 增加单相机正常方程和状态更新测试。


阶段2：引入多相机输入和CameraContext

1. 支持相机配置列表；
2. 支持多个图像订阅和同步RigFrame；
3. 每个相机加载独立模型和外参；
4. 暂时不修改优化结果。


阶段3：拆分视觉处理接口

将processFrame()拆成：

1. prepareFrameAndObservations()；
2. linearizeObservations()；
3. commitMapUpdates()。

先保证单相机经过新接口后与旧实现结果一致。


阶段4：实现多相机联合正规方程

1. 所有相机基于同一状态线性化；
2. 累加A和b；
3. 每个金字塔层、每次迭代只联合更新一次；
4. 验证相机顺序不影响结果。


阶段5：改造共享视觉地图

1. 增加camera_id和rig_frame_id；
2. 将单一ref_patch改为参考候选集合；
3. 实现新点候选合并和去重；
4. 按唯一机体位姿而不是观测条数判断收敛；
5. 统一地图所有权和观测裁剪。


阶段6：实现每相机曝光参数

1. 将当前单个inv_expo_time扩展为每相机参数；
2. 确保每条残差只写入当前相机对应的曝光雅可比列；
3. 为曝光参数加入先验或固定主相机尺度；
4. 验证曝光关闭时的固定亮度路径。


阶段7：性能优化和并行化

1. 总点数预算；
2. 参考候选裁剪；
3. 线程局部正规方程；
4. 每相机并行线性化；
5. 性能统计和异常相机隔离。


十八、建议的验证清单
--------------------

1. 单相机退化测试
   只启用一个相机时，新代码应与当前单相机结果基本一致。

2. 相机顺序不变性
   正序和逆序处理相机时，A、b和最终状态应一致或只存在浮点误差。

3. 堆叠与累加等价性
   显式堆叠H/r和流式累加正规方程应得到相同状态增量。

4. 跨相机几何雅可比数值检查
   使用有限差分验证位姿雅可比，尤其验证相机基线平移项。

5. 同时可见点去重
   同一世界点被多个相机看到时只能创建一个VisualPoint。

6. 参考候选选择
   当前相机应能选择其他相机产生的参考patch，并正确使用T_virtual_reference_world。

7. 曝光雅可比稀疏性
   camera_i的残差只能更新camera_i的曝光参数，不能写入其他相机曝光列。

8. 相机缺帧和异常测试
   单个相机缺帧、模糊或无有效点时，其余相机仍能完成联合更新。

9. 地图批量提交测试
   残差构造期间地图内容不得变化，所有地图修改只能发生在联合优化之后。

10. 内存稳定性测试
    长时间运行时VisualPoint、Feature和虚拟支持图数量应保持有界。


十九、当前结论
--------------

1. “逐相机构造残差，所有相机统一优化”在数学和工程上都是合理的。

2. 时间同步后，多个相机可以共享同一个机体状态线性化点。

3. 跨相机patch是成立的，但必须使用完整相机模型、完整相机外参以及包含基线平移的SE(3)
   相对变换，不能只做旋转映射。

4. 参考patch可以由共享地图统一管理，选择时不限制源相机；但参考观测仍必须保存源相机身份、
   参考相机位姿和参考虚拟patch坐标系。

5. 共享视觉地图中，世界点数据可以继续复用；需要重点改造的是多相机观测、参考候选、
   收敛统计、新点去重和对象所有权。

6. 多相机版本应使用每相机独立的光度参数。每条残差只优化共享位姿和当前相机对应的
   光度参数。

7. 曝光估计不是必需功能，由vio.exposure_estimate_en控制。当前项目默认和主要YAML配置中
   均为开启状态。

8. 计算量增加主要来自patch构造、warp和像素残差，而不是最终小维度状态求解。

9. 推荐先完成正确的顺序联合优化和共享地图批量提交，再进行多线程并行化。

10. 该扩展整体属于中高到高难度。真正的难点是共享地图的观测管理和前端/优化/地图提交
    三阶段解耦，而不是联合正规方程本身。
