你需要在当前 FAST-LIVO2 / VIO 代码基础上实现多相机 direct VIO 支持。请严格按下面要求改，不要自行改变架构，不要引入未要求的新概念。本文明确要求的 PerCameraData、PendingImageGroup、MultiCameraFrame、PendingNewPointObservation 只是实现所需的数据结构，不代表新增 VIOManager、地图、状态或新的算法架构。

当前已有文件包括但不限于：

* LIVMapper.cpp
* vio_fisheye.cpp / vio_fisheye.h
* frame_fisheye.cpp / frame.h
* feature_fisheye.h
* common_lib.h
* 以及 StatesGroup、IMU propagation、VIO update 相关文件

总体目标：
在不创建多个 VIOManager 的前提下，让一个 VIOManager 支持多个同步相机。所有相机共享同一个视觉地图 feat_map，共享同一个状态。每个相机只拥有自己的相机模型、外参、图像缓存、grid、LUT、SubSparseMap、Frame、debug 图等 per-camera 临时数据。

绝对硬约束：

1. 只能有一个 VIOManager。
2. 只能有一个共享视觉地图 feat_map。
3. 不要把多相机图像拼成一张图参与算法。多相机输入只是一个容器，images[camera_id] 保存每个相机自己的原始图像。
4. raw patch 和 virtual patch 都必须支持多相机。virtual_fisheye_patch_en 只决定 patch/warp/projection 路径，不能决定是否支持多相机。
5. raw patch 和 virtual patch 在跨相机参考时本质一样：reference patch 所属 camera_id 和 current observation 所属 camera_id 可能不同。任何地方都不能默认 ref_ftr->camera_id_ == current_camera_id_，除非 cross_camera_reference_en=false。
6. 不新增 rig_frame_id。继续使用原来的 id_ 语义。
7. 同一 timestamp 下多个相机的 Frame::id_ 必须相同。id_ 表示离散帧时间/第几帧。camera_id_ 表示来自哪个相机。
8. 多相机观测身份不能用 id_ 单独判断。判断是否同一观测时必须 id_ 和 camera_id_ 都一致；判断是否同一个 Feature 对象时优先使用指针比较。
9. 不要用 “id_ + camera_id_” 数值相加或拼接作为模糊 key。若需要 key，必须显式使用二元结构 {id_, camera_id_}。
10. 新视觉点创建不能按空间距离阈值合并。只有明确来自同一个 source identity，例如同一帧的 pg[i]，才允许合并到同一个 VisualPoint。
11. 当前任务需要实现第一版多相机点云着色，但只允许采用顺序 first-hit 策略：按 camera_id 从小到大依次尝试给未着色点上色，已经成功着色的点不再被后续相机处理。不要实现最佳相机选择、遮挡判断、曝光补偿、多相机颜色融合，也不要为每个相机发布一份完整彩色点云。


一、多相机配置

参数文件组织形式要求：

当前工程继续采用“主配置 YAML + 相机内参 YAML 分离”的方式。不要把相机内参、畸变参数、camera model 塞进主配置文件。相机内参仍然放在单独的 camera YAML 文件中，保持原工程 vk::camera_loader::loadFromRosNs() 的读取方式。

一、主配置 YAML 的组织方式

主配置 YAML 中只放系统参数、LiDAR/IMU 参数、VIO 参数、每个相机的图像 topic、每个相机的 LiDAR-to-camera 外参，以及每个相机对应的内参 namespace。

1. common.num_cameras 是相机数量。camera_id 从 0 到 num_cameras-1。
2. cameras.camera{i} 是第 i 个相机的配置域。
3. cameras.camera{i}.img_topic 是第 i 个相机的图像 topic。
4. cameras.camera{i}.camera_ns 是第 i 个相机在相机内参 YAML 中的 namespace，用于 vk::camera_loader::loadFromRosNs(node, camera_ns, cam)。
5. cameras.camera{i}.Rcl / cameras.camera{i}.Pcl 是第 i 个相机的 LiDAR-to-camera 外参，继续保持原来单相机 Rcl/Pcl 的格式，不要改成 Rcl_list/Pcl_list，不要改成二维数组，不要改成扁平总数组。
6. extrin_calib.extrinsic_T / extrin_calib.extrinsic_R 仍然只表示 LiDAR-to-IMU 外参，只有一组。
7. 相机外参不要再从 extrin_calib.Rcl / extrin_calib.Pcl 读取。所有相机外参统一从 cameras.camera{i}.Rcl / cameras.camera{i}.Pcl 读取。
8. common.img_topic 不再作为多相机 direct VIO 的图像入口。即使 num_cameras=1，也应使用 cameras.camera0.img_topic。
9. 用户会保证至少存在 cameras.camera0，因此不要设计复杂的 legacy fallback 逻辑。num_cameras=1 时也按 cameras.camera0 读取。
10. 不要引入 common.img_topics、common.camera_namespaces、extrin_calib.Rcl_list、extrin_calib.Pcl_list。参数组织必须使用 cameras.camera{i} 域。

三、代码读取规则

readParameters() / initializeComponents() 必须按以下逻辑读取：

1. 读取 common.num_cameras。
2. 检查 num_cameras >= 1。
3. 对每个 camera_id = 0 ... num_cameras-1：

   * 构造配置域名：
     cam_cfg_ns = "cameras.camera" + std::to_string(camera_id)
   * 读取 cam_cfg_ns + ".img_topic"
   * 读取 cam_cfg_ns + ".camera_ns"
   * 读取 cam_cfg_ns + ".Rcl"
   * 读取 cam_cfg_ns + ".Pcl"
   * 检查 Rcl.size() == 9
   * 检查 Pcl.size() == 3
   * 使用 camera_ns 调用 vk::camera_loader::loadFromRosNs(node, camera_ns, cameras_[camera_id].cam)
4. 如果任何 cameras.camera{i} 缺少 img_topic、camera_ns、Rcl、Pcl，必须直接 throw runtime_error，不要静默 fallback。
5. 如果 camera_loader 无法从 camera_ns 加载相机模型，必须直接 throw runtime_error，并在错误信息中打印 camera_id 和 camera_ns。
6. extrin_calib.extrinsic_T / extrin_calib.extrinsic_R 只读取一次，用于 setImuToLidarExtrinsic / IMU-LiDAR 外参。
7. 不要再调用旧的 setLidarToCameraExtrinsic(cameraextrinR, cameraextrinT) 作为全局单相机外参入口。应为每个 PerCameraData 写入自己的 Rcl/Pcl，并在初始化每个相机上下文时计算自己的 Rci/Pci/Rcw/Pcw/Jdphi_dR/Jdp_dR 等。
8. num_cameras=1 时也走同一套 cameras.camera0 读取路径，不要再写旧 common.img_topic + extrin_calib.Rcl/Pcl 的复杂兼容分支。

四、图像 subscriber 参数读取规则

图像 subscriber 必须根据 common.num_cameras 动态创建。

1. 不要继续只使用一个 img_topic / sub_img / sub_img_compressed。
2. 对每个 camera_id，使用 cameras.camera{i}.img_topic 创建一个 subscriber。
3. 每个 subscriber 的 callback 必须捕获自己的 camera_id。
4. 同一 timestamp 下不同 camera_id 的图像允许具有完全相同 ROS header stamp，不能因为 timestamp 相同被当成重复图像丢弃。
5. 重复图像判断必须按 camera_id 独立执行，或者在 pending_images[stamp_ns] 中按 camera_id 判断是否已经收到该 timestamp 的该相机图像。
6. pending_images 的 key 使用原始 ROS header stamp 转成的整数纳秒 stamp_ns。不要使用加了 img_time_offset 之后的 double 时间作为 map key。
7. MultiCameraFrame.timestamp 可以使用 stamp_ns 转秒后加 img_time_offset，但组包 key 必须是原始 stamp_ns。
8. 当同一个 stamp_ns 下所有 camera_id 图像都到齐后，生成 MultiCameraFrame，并分配一个 shared_frame_id。
9. VIO 创建每个相机 Frame 时，必须显式设置 frame->id_ = meas.multi_cam_frame.frame_id，或 frame->id_ = mf.frame_id，其中 mf 必须是 meas.multi_cam_frame 的 const 引用。不要让 Frame 构造函数对同一 timestamp 的每个相机分别 frame_counter_++ 产生不同 id_。

二、主程序 LIVMapper.cpp 多相机同步

将原来的单图像 img_buffer/img_time_buffer 改造成多相机同步组包逻辑。

定义类似结构：

struct MultiCameraFrame {
  uint64_t stamp_ns = 0;              // 原始 ROS header stamp 转成的整数纳秒，只用于精确同步和 debug
  double timestamp = 0.0;             // stamp_ns 转秒后加 img_time_offset，供 sync_packages / VIO 使用
  int frame_id = -1;                  // 同一 timestamp 下所有 camera Frame 共用的 id_
  std::vector<cv::Mat> images;        // images[camera_id]
};

补充定义：

struct PendingImageGroup {
uint64_t stamp_ns = 0;
double timestamp = 0.0;
std::vector<cv::Mat> images;      // images[camera_id]
std::vector<uint8_t> arrived;     // arrived[camera_id]

bool isComplete() const {
if (arrived.empty()) return false;
for (uint8_t v : arrived) {
if (!v) return false;
}
return true;
}
};


PendingImageGroup 只用于 LIVMapper.cpp 的 callback 组包缓存。它可以是不完整的，不能进入 sync_packages，不能进入 VIO。

当 PendingImageGroup::isComplete() 为 true 时，才生成完整 MultiCameraFrame，分配 shared_frame_id，并把完整 MultiCameraFrame 放入图像同步 buffer。

主程序收到每个相机图像后：

* MultiCameraFrame.frame_id 必须在该 timestamp 的所有相机图像到齐、生成 MultiCameraFrame 时分配一次。后续 VIO 创建每个 camera Frame 时，所有 camera Frame 都使用这个相同的 frame_id。
* 根据原始 ROS header stamp 精确分组。
* pending_images[stamp_ns].images[camera_id] = image。
* 当同一个 stamp_ns 下所有 camera_id 图像都到齐，生成一个 MultiCameraFrame，timestamp 使用该 stamp 对应时间。
* 送入原有 LIVO sync pipeline。
* sync_packages() 仍然只用一个统一图像 timestamp 切 LiDAR / IMU，不要为每个相机单独切 LiDAR / IMU。

MeasureGroup 修改：

* 继续复用现有 MeasureGroup 作为 LIVO pipeline 的同步输出，不要绕开 sync_packages 重新设计一套主流程。
* 原来的 cv::Mat img 保留，用于 frontend_mode=1/2、camera_id=0 fallback、旧 debug 路径；它不代表继续使用旧 common.img_topic 配置入口。
* MeasureGroup 新增：
  MultiCameraFrame multi_cam_frame;
  bool has_multi_cam_frame = false;
* num_cameras>=1 且 frontend_mode=0 时，sync_packages 输出的 MeasureGroup 必须设置：
  meas.multi_cam_frame = 对应 timestamp 的多相机图像组；
  meas.has_multi_cam_frame = true；
  meas.img = meas.multi_cam_frame.images[0]；
  meas.img_time = meas.multi_cam_frame.timestamp；
* frontend_mode=0 使用 meas.multi_cam_frame 执行多相机 direct VIO。
* frontend_mode=1/2 光流或 fake 路径在 num_cameras>1 时只使用 meas.img，也就是 camera_id=0，不要报错。

五、StatesGroup 动态多曝光状态

必须全局改造 StatesGroup，不要继续固定 DIM_STATE=19。

原始非曝光状态维度为 18：
rot 3
pos 3
vel 3
bias_g 3
bias_a 3
gravity 3

多相机状态维度：
state_dim = 18 + num_cameras

建议索引设计：
rot:              0~2
pos:              3~5
inv_expo[cid]:    6 + cid
vel:              6 + num_cameras ~ 8 + num_cameras
bias_g:           9 + num_cameras ~ 11 + num_cameras
bias_a:           12 + num_cameras ~ 14 + num_cameras
gravity:          15 + num_cameras ~ 17 + num_cameras

num_cameras=1 时必须等价于旧 DIM_STATE=19。

StatesGroup 要求：

* 保存 int num_cameras 或能访问全局状态维度。
* inv_expo_time 改成 Eigen::VectorXd 或 std::vector<double>。
* cov 改成动态 Eigen::MatrixXd。
* operator+、operator+=、operator- 改成动态 VectorXd。
* 所有 H_T_H、G、K、solution、state covariance update 等矩阵必须按 state_dim 动态生成。
* IMU propagation、process noise、cov propagation 中所有固定 DIM_STATE 相关代码都要同步改。
* 曝光状态可以按随机游走或保持原逻辑中的先验处理，但每个 camera_id 有独立曝光状态。
* 初始化时仍允许配置一个 scalar inv_expo_time_init，并复制给所有 camera。
* 每条视觉残差只对当前 camera_id 的曝光状态写雅可比，即列 index 为 6 + current_camera_id。

残差曝光逻辑：
ref_ftr->inv_expo_time_ 保存参考 Feature 创建时的对应相机曝光值。
当前帧 residual 使用 state->inv_expo_time[current_camera_id]。
不能所有相机共用一个曝光状态。

六、多相机处理流程

重构 processFrame，不要简单循环调用旧 processFrame 后直接改地图。

新流程建议：

建议新增或改造 VIO 入口为：
VIO 入口统一使用：

processMultiCameraFrame(const MeasureGroup& meas, pointWithVar* pg, ...)

VIOManager 必须从 meas.multi_cam_frame 读取多相机图像、timestamp、frame_id。不要新增绕开 MeasureGroup 的独立 VIO 同步入口。MultiCameraFrame 只是 MeasureGroup 内部携带的完整多相机图像容器。

processMultiCameraFrame 内部可以写：

const MultiCameraFrame& mf = meas.multi_cam_frame;

但 mf 必须只是 meas.multi_cam_frame 的 const 引用，不允许让 VIO 入口直接脱离 MeasureGroup 重新同步 LiDAR/IMU。

1. 对每个 camera_id：

   * 读取对应图像
   * resize / grayscale / rgb debug
   * 创建 PerCameraData::new_frame
   必须使用：

   new_frame->id_ = meas.multi_cam_frame.frame_id;
   new_frame->camera_id_ = camera_id;
   new_frame->timestamp_ = meas.multi_cam_frame.timestamp;

   不要在这里使用单独的 mf 变量，除非 mf 是 meas.multi_cam_frame 的 const 引用。
   * 根据当前 state 和该相机外参更新该相机 frame pose
   * reset 该相机 grid / visual_submap / 临时缓存

2. 对每个 camera_id 顺序执行前端观测准备：

   * retrieveFromVisualSparseMapMultiCamera(camera_id, ...)
   * generateVisualMapPointSelections(camera_id, ...)
   * 注意：这一步只读取旧 feat_map，不允许立即 insertPointIntoVoxelMap。
   * 每个相机都只看进入该 multi-camera frame 前已经存在的旧地图。
   * 顺序执行前端提取可以接受，但不能让先处理的相机插入的新点影响后处理的相机。

3. 联合视觉更新：

   * 所有相机的 visual_submap 都准备好后，在同一个 state linearization 下联合构造视觉更新。
   * 每个相机各自 linearize residual，然后累加到同一个 H_T_H / HTz / G / solution。
   * 每条 residual 使用对应 current_camera_id 的相机模型、外参、图像、SubSparseMap、曝光状态。
   * 不要给每个相机单独更新一次状态后再下一个相机。应该是多相机联合观测更新同一个状态。

4. 更新所有相机 frame pose：

   * 状态更新完成后，用最终 state 更新每个 PerCameraData::new_frame 的 pose。

5. 统一提交新视觉点：

   * 所有相机前端筛选通过的新观测统一创建/挂接 VisualPoint 和 Feature。
   * 然后统一 insertPointIntoVoxelMap。
   * 再统一更新 reference patch cache。

七、新视觉点创建：延迟提交，不重新筛选

原始 generateVisualMapPoints / generateVisualMapPointsVirtual 的 grid + ShiTomasi 筛选逻辑必须保留。

不要在 commit 阶段重新做投影、grid、ShiTomasi、NCC 等筛选。

需要做的只是：

* 原来筛选通过后立即 new VisualPoint + new Feature + insertPointIntoVoxelMap。
* 现在改成先生成待提交观测 PendingNewPointObservation。
* 所有相机完成后，再统一 commit。

八、reference patch 策略

保留 FAST-LIVO2 的 reference patch cache/update 思路：

* 不要每帧无条件重新选择 ref patch。
* 谁新增了新的 Feature，谁触发对应 reference cache 更新。
* ref patch 选择不需要面向当前帧每次重选。

新增配置：
vio.cross_camera_reference_en

当 cross_camera_reference_en=true：

* 每个 VisualPoint 只使用一个全局 ref_patch_ / has_ref_patch_。
* 所有 camera_id 的 Feature 都可以参与竞争成为该 VisualPoint 的全局 reference patch。
* 当前相机可以使用其他相机的 ref patch。
* 但使用时必须完整处理 ref camera 与 current camera 不同的情况。

当 cross_camera_reference_en=false：

* 每个 VisualPoint 必须为每个 camera_id 维护独立 reference cache：
  std::vector<Feature*> ref_patch_by_camera_;
  std::vector<uint8_t> has_ref_patch_by_camera_;
* 当前 camera_id 只能从同 camera_id 的 Feature 里选择 reference patch。
* 当前 camera_id 只能使用 ref_patch_by_camera_[current_camera_id]。
* 如果当前 VisualPoint 没有当前 camera_id 的历史 Feature，则该相机不能用这个 VisualPoint 构造 photometric residual。

删除 Feature 时必须保证缓存安全：

* 如果删除的是 pt->ref_patch_，必须清空或重新选择 global ref patch。
* 如果删除的是 pt->ref_patch_by_camera_[cid]，必须清空或重新选择该 cid 的 ref patch。
* deleteFeatureRef()、deleteNonRefPatchFeatures()、obs_ 超限删除逻辑都要检查。
* 不能留下悬空 Feature*。

updateReferencePatch 重构：

* cross_camera_reference_en=true 时，从 pt->obs_ 全部 Feature 中评分，更新 global ref_patch_。
* cross_camera_reference_en=false 时，只更新新增 Feature 所属 camera_id 的 ref_patch_by_camera_[camera_id]，候选集只允许同 camera_id。
* 评分逻辑可以沿用 FAST-LIVO2 的 NCC + cos_angle 逻辑。
* 注意 cos_angle 是候选参考帧自己的 viewing ray 与点法向关系，不是当前帧和参考帧的 close-view 匹配。

九、raw patch 与 virtual patch 的跨相机要求

这一节必须严格实现，避免错误假设。

共同要求：

* raw patch 和 virtual patch 都必须支持 ref camera 与 current camera 不同。
* virtual patch 并不是全局统一相机坐标系。
* 每个 virtual patch 都是“某个真实 camera_id + 某个 patch 中心方向”定义出来的局部虚拟相机。
* 不能因为 virtual patch 被重采样到虚拟针孔平面，就忽略 ref_ftr->camera_id_。
* 任何地方都不能复用单相机全局 cam/Rcl/Pcl/Rcw/Pcw 来处理所有相机。
* 必须从 cameras_[ref_ftr->camera_id_] 取 reference camera context，从 cameras_[current_camera_id] 取 current camera context。

raw patch：

* ref patch 保存在 ref camera 的原始图像坐标系。
* current residual 在 current camera 的原始图像坐标系采样。
* 跨相机 warp 必须同时使用 ref_cam 和 cur_cam。
* getWarpMatrixAffineHomography / getWarpMatrixAffine / warpAffine 相关接口必须改造，不能只传一个 cam。
* ref camera 的 cam2world 用于解释 ref_ftr->px_ / ref patch。
* current camera 的 world2cam 用于投影到当前图像。
* 相对位姿必须由 ref camera pose 和 current camera pose 计算，不能假设同相机。

virtual patch：

* ref Feature 必须保存自己的 camera_id_、T_v_w_、R_v_from_c_、R_c_from_v_、virtual_patch_valid_。
* ref virtual patch 的构造依赖 ref_ftr->camera_id_ 对应的真实相机模型、真实相机外参、参考图像和虚拟旋转。
* current virtual patch / current residual 的构造依赖 current_camera_id 对应的真实相机模型、真实相机外参、当前图像和当前虚拟旋转。
* 跨相机时使用：
  T_vcur_vref = T_vcur_w * T_vref_w.inverse()
* T_vcur_w 必须由 current camera 的真实外参 + 当前虚拟旋转得到。
* T_vref_w 必须由 ref Feature 自己保存的 ref virtual pose 得到。
* 虚拟针孔内参可以所有相机共用，但虚拟位姿、raw image 采样、曝光状态都必须绑定到各自 camera_id。
* virtual patch 对 viewing-angle dot product 可保持旋转点积不变的性质，但投影、warp、patch 采样、雅可比必须使用虚拟相机位姿。

十、SubSparseMap

SubSparseMap 是每相机当前帧临时观测容器，不是地图。

多相机下：

* 每个 PerCameraData 拥有一个 SubSparseMap visual_submap。
* 每个相机 reset 自己的 visual_submap。
* 联合 update 时遍历所有 camera 的 visual_submap。
* 共享地图仍然只有 VIOManager::feat_map。

十四、点云着色

本任务第一版需要实现多相机点云着色，但采用最简单的顺序 first-hit 策略，不实现最佳相机选择、遮挡判断、曝光补偿或多相机颜色融合。

点云着色策略如下：

1. 最终只发布一份彩色点云，不要为每个相机发布一份完整彩色点云。
2. 多相机着色按 camera_id 从小到大顺序执行，即 camera0、camera1、camera2、...
3. 对待发布点云中的每个点维护一个 colored mask：
   std::vector<uint8_t> colored(point_num, 0);
4. 每个相机只处理 colored[i] == 0 的点。
5. 如果某个点能成功投影到当前 camera_id 的图像中，并成功采样颜色，则：

   * 写入该点 RGB 颜色；
   * 设置 colored[i] = 1；
   * 后续 camera_id 不再处理该点。
6. 如果一个点在所有相机中都无法成功投影或采样颜色，则该点可以不进入 RGB 点云，或者保留 intensity fallback；但系统不能崩溃，不能发布非法颜色。
7. 不要在遍历过程中删除点，必须使用 colored mask 标记是否已着色，避免索引错乱。
8. 不要实现基于空间距离、图像中心距离、视角夹角、遮挡判断的最佳相机选择。第一版只按 camera_id 顺序 first-hit。
9. 不要把多相机图像拼接后再着色。每个相机必须使用自己的 camera model、Frame pose、img_rgb 单独投影和采样。

建议在 VIOManager 中封装统一接口：

int camera_id,
const V3D& p_w,
V3F& bgr,

该函数内部必须：

1. 检查 camera_id 是否合法。
2. 从 cameras_[camera_id] 获取该相机的 PerCameraData。
3. 检查 ctx.cam、ctx.new_frame、ctx.img_rgb 是否有效。
4. 使用该相机自己的 Frame pose 将世界点 p_w 转到当前相机坐标系。
5. 使用该相机自己的 camera model 投影到图像坐标。
6. 检查投影是否在该相机图像范围内。
7. 从 ctx.img_rgb 中双线性采样颜色。
8. 成功则返回 true，否则返回 false。
9. 如果 getInterpolatedPixel() 不是 const 成员函数，则 getColorFromCamera() 可以不声明为 const，优先保证可编译。

publish_frame_world() 中禁止继续隐式使用单相机全局变量，例如：

* vio_manager->img_rgb
* vio_manager->new_frame_
* vio_manager->cam

十六、预期最终流程摘要

最终 direct VIO 流程应为：

1. LIVMapper 收到各相机图像，按相同 ROS timestamp 精确组包。
2. 所有相机到齐，生成 MultiCameraFrame，并放入图像同步 buffer。
3. sync_packages 用统一 timestamp 切 LiDAR / IMU。
4. sync_packages 输出包含 multi_cam_frame 的 MeasureGroup，VIOManager::processMultiCameraFrame 接收 sync_packages 输出的 MeasureGroup，并从 meas.multi_cam_frame 读取多相机图像组。
5. 为每个 camera_id 创建/更新 Frame，所有 Frame 共享同一个 id_，但 camera_id_ 不同。
6. 每个相机独立 reset grid 和 SubSparseMap。
7. 每个相机顺序执行旧逻辑的观测检索和新点筛选，但只读取旧地图，不写 feat_map。
8. 所有相机 visual_submap 完成后，联合构造视觉残差并更新同一个 state。
9. 更新所有相机 Frame pose。
10. 统一提交所有相机筛选通过的新 Feature / VisualPoint。
11. 按 cross_camera_reference_en 更新 global ref_patch 或 per-camera ref_patch_by_camera_。
12. 发布所有相机 debug 图。
13. 点云着色采用顺序 first-hit 多相机着色：camera0、camera1、camera2、... 依次尝试为未着色点补色，已经着色的点不再被后续相机处理，最终只发布一份 RGB 点云。若所有相机都无法为某些点着色，则这些点不进入 RGB 点云，或在 RGB 点云为空时 fallback 发布累计后的 intensity cloud。


额外的提醒：
deleteNonRefPatchFeatures() 不能继续只保留全局 ref_patch。当 cross_camera_reference_en=false 时，必须保留所有 ref_patch_by_camera_[cid] 指向的 Feature，不能删除任何相机当前 reference cache 使用的 Feature。deleteFeatureRef() 删除 Feature 时，也必须同步检查 global ref_patch_ 和所有 ref_patch_by_camera_。

所有依赖 cam/width/height/fx/fy/cx/cy/raw_pixel_to_unit_ray_lut_/raw_pixel_unit_ray_valid_mask_/Rcw/Pcw/Rci/Pci 的函数，必须改为显式传入 PerCameraData& ctx 或 camera_id。禁止 helper 函数内部隐式使用 VIOManager::cam/VIOManager::width/VIOManager::Rcw 等单相机全局变量处理多相机数据。

多相机下，不能使用一个全局 last_timestamp_img 对所有图像做“时间过近/重复图像”过滤。该过滤必须按 camera_id 独立执行，或者直接在 pending_images[stamp_ns] 中按 camera_id 判断重复。允许 camera0/camera1/... 拥有完全相同 timestamp；不能因此丢弃后到达的其他相机图像。

Frame::id_ 不应在图像 callback 阶段生成。这里的 frame_id 是 MultiCameraFrame 的共享帧编号，不是直接创建 Frame 对象。图像 callback 可以在完整 PendingImageGroup 转成 MultiCameraFrame 时分配 shared_frame_id，但绝对不能在每个单相机 callback 中分别创建 Frame 或让 Frame::frame_counter_++。
图像 callback 只做按 stamp_ns + camera_id 的组包。
当一个 timestamp 下所有相机图像到齐并生成 MultiCameraFrame 时，才执行 next_vio_frame_id++，并把这个 shared_frame_id 写入 MultiCameraFrame。
VIO 创建每个 camera Frame 时，必须显式设置 frame->id_ = multi_cam_frame.frame_id。
同一个 MultiCameraFrame 内所有 camera Frame 的 id_ 相同，camera_id_ 不同。

图像 subscriber 必须按 common.num_cameras 动态创建。

当前问题：

flushCompletedImageGroupsLocked() 只检查 pending_images.begin()。如果最旧 timestamp 的 PendingImageGroup 不完整，就直接 break。这样会导致后面已经完整的多相机帧被旧的不完整 group 阻塞，直到 pending_images.size() 超过 multi_cam_sync_queue_size 后才释放。这会造成不必要的图像延迟和同步抖动。

需要实现的策略：

采用 “later-complete 触发 stale incomplete drop” 策略。

核心要求：

1. pending_images 仍然使用 std::map<uint64_t, PendingImageGroup>，按 stamp_ns 有序保存未 flush 的 group。
2. multi_cam_frame_buffer 只能包含完整 MultiCameraFrame。
3. multi_cam_frame_buffer 必须保持 stamp_ns 单调递增，不能把较新完整 group 直接 push 到较旧未处理 group 前面。
4. flushCompletedImageGroupsLocked() 仍然只能从 pending_images.begin() 开始按时间顺序处理。
5. 如果 oldest group 已完整：

   * 生成 MultiCameraFrame；
   * frame.stamp_ns = oldest->second.stamp_ns；
   * frame.timestamp = oldest->second.timestamp；
   * frame.frame_id = next_vio_frame_id++；
   * frame.images = std::move(oldest->second.images)；
   * push_back 到 multi_cam_frame_buffer；
   * erase oldest；
   * continue 继续检查下一个 oldest。
6. 如果 oldest group 不完整，但 pending_images 中存在更晚 timestamp 的完整 group：

   * 认为 oldest group 已经 stale；
   * warning 打印该 stamp_ns 以及缺失的 camera_id；
   * erase oldest；
   * continue 继续 flush。
7. 如果 oldest group 不完整，且不存在任何更晚 timestamp 的完整 group：

   * 停止 flush；
   * break；
   * 等待后续图像到达。
8. 保留 pending_images.size() > multi_cam_sync_queue_size 的兜底丢弃逻辑，但它只作为兜底，不应该是解除旧残帧阻塞的唯一机制。
9. next_vio_frame_id++ 只能在完整 MultiCameraFrame 真正 push 到 multi_cam_frame_buffer 时执行，不能在 PendingImageGroup 刚 complete 时提前执行。
10. 不要改变 handleImageFrame() 的基本组包逻辑：callback 仍然只负责按 stamp_ns + camera_id 填充 pending_images，并在写入新图像后调用 flushCompletedImageGroupsLocked()。

建议实现辅助函数：

static 或成员函数均可，但不要引入新架构。

可以新增：

bool LIVMapper::hasLaterCompleteImageGroupLocked(uint64_t stamp_ns) const;

语义：

从 pending_images.upper_bound(stamp_ns) 开始遍历，如果发现任意 it->second.isComplete() == true，则返回 true，否则返回 false。

语义：

遍历 group.arrived，如果 arrived[camera_id] == 0，则把 camera_id 加入字符串，用于 warning。该函数只用于日志，不影响逻辑。

注意：

1. 不允许在 handleImageFrame() 中发现当前 group complete 后直接 push_back 到 multi_cam_frame_buffer，因为这可能造成 multi_cam_frame_buffer 时间乱序。
2. 不允许遍历 pending_images 找到任意完整 group 就直接 push_back，必须保证输出顺序。
3. 只有当更早的不完整 group 被判定 stale 并丢弃后，后面的完整 group 才能按顺序 flush。
4. queue 超限逻辑仍然可以保留：

while (static_cast<int>(pending_images.size()) > multi_cam_sync_queue_size)
{
const uint64_t dropped_stamp = pending_images.begin()->first;
const std::string missing = formatMissingCameraIdsLocked(pending_images.begin()->second);
pending_images.erase(pending_images.begin());

RCLCPP_WARN(
this->node->get_logger(),
"Drop incomplete multi-camera group stamp_ns=%llu due to pending queue overflow, missing cameras=%s",

5. 该修复只改变 pending_images 到 multi_cam_frame_buffer 的 flush 策略，不改变 sync_packages() 对 multi_cam_frame_buffer.front() 的使用方式。
6. 修复后应满足：

   * 不完整旧帧不会长期阻塞后续完整帧；
   * multi_cam_frame_buffer 内的 MultiCameraFrame 仍然按 stamp_ns 单调递增；
   * frame_id 仍然按真正进入 VIO 的完整帧顺序递增；
   * 只有完整 MultiCameraFrame 能进入 sync_packages / VIO。
补充约束：

1. 如果新增 hasLaterCompleteImageGroupLocked()、formatMissingCameraIdsLocked() 作为 LIVMapper 成员函数，必须同时在 LIVMapper_multi_cam.h 中声明；如果只在 cpp 内部作为 lambda 或 static helper，则不需要改 header。优先保证可编译。

2. flushCompletedImageGroupsLocked()、hasLaterCompleteImageGroupLocked()、formatMissingCameraIdsLocked() 都默认在已经持有图像组包 mutex 的情况下调用，不要在这些函数内部重复加锁，避免死锁。

3. formatMissingCameraIdsLocked() 必须在 erase oldest 或 move images 之前调用；不要在 std::move(oldest->second.images) 之后再访问该 group 的图像内容。

4. handleImageFrame() 写入 pending_images[stamp_ns].images[camera_id] 后，只调用 flushCompletedImageGroupsLocked()。即使当前 group 已 complete，也不能在 handleImageFrame() 中直接 push_back 到 multi_cam_frame_buffer，避免时间戳乱序。
